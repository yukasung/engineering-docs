# Django Error Handling — ส่ง Error ที่ React แยกสาเหตุได้

## เรื่องนี้คืออะไร?

Error handling คือวิธีตอบเมื่อคำขอไม่สำเร็จ ให้ผู้ใช้รู้ว่าควรแก้อะไรและทีมตรวจสาเหตุได้ ตัวอย่างใช้ Envelope เดียวคือ `error.code`, `message`, `details` ไม่ส่ง Exception ดิบให้ Browser

## ใช้เมื่อไร?

ใช้กับ Validation, Session หมดอายุ, CSRF, สิทธิ์, ไม่พบข้อมูล และข้อผิดพลาดภายใน

## ตัวอย่าง Code

DRF ปกติอาจตอบ Validation เป็น `{"title":["..."]}` หรือ Error ทั่วไปเป็น `{"detail":"..."}` โค้ดด้านล่าง **ปรับรูปแบบ** ผ่าน `EXCEPTION_HANDLER` ใน Settings ไม่ใช่ Default ที่ DRF สร้างให้เอง:

```python filename="backend/api/errors.py"
import logging
from django.http import JsonResponse
from rest_framework.exceptions import (
    APIException, AuthenticationFailed, NotAuthenticated, ValidationError,
)
from rest_framework.response import Response

logger = logging.getLogger(__name__)


class CsrfFailed(APIException):
    status_code = 403
    default_detail = "CSRF verification failed"
    default_code = "csrf_failed"


class InvalidCredentials(APIException):
    status_code = 403
    default_detail = "Invalid credentials"
    default_code = "invalid_credentials"


class Conflict(APIException):
    status_code = 409
    default_detail = "Conflict"
    default_code = "conflict"


def envelope(code, message, details=None):
    return {"error": {"code": code, "message": message, "details": details or {}}}


def exception_handler(exc, context):
    # Import ตอนเรียกใช้ เพื่อไม่วนกับ DEFAULT_AUTHENTICATION_CLASSES
    from rest_framework.views import exception_handler as drf_exception_handler

    response = drf_exception_handler(exc, context)
    if response is None:
        request = context.get("request")
        logger.error("unhandled_api_error", extra={
            "exception_type": type(exc).__name__,
            "method": getattr(request, "method", None),
            "path": getattr(request, "path", None),
        })
        return Response(envelope("INTERNAL_ERROR", "ระบบขัดข้อง กรุณาลองใหม่ภายหลัง"), status=500)

    details = {}
    if isinstance(exc, CsrfFailed):
        code, message = "CSRF_FAILED", "กรุณาโหลดหน้าใหม่แล้วลองอีกครั้ง"
    elif isinstance(exc, InvalidCredentials):
        code, message = "INVALID_CREDENTIALS", "ชื่อผู้ใช้หรือรหัสผ่านไม่ถูกต้อง"
    elif isinstance(exc, (NotAuthenticated, AuthenticationFailed)):
        code, message = "AUTHENTICATION_REQUIRED", "กรุณาเข้าสู่ระบบอีกครั้ง"
    elif isinstance(exc, ValidationError):
        code, message = "VALIDATION_ERROR", "ข้อมูลไม่ถูกต้อง"
        details = response.data
        if not isinstance(details, dict):
            details = {"non_field_errors": details}
    else:
        code, message = {
            400: ("BAD_REQUEST", "รูปแบบคำขอไม่ถูกต้อง"),
            403: ("PERMISSION_DENIED", "ไม่มีสิทธิ์ทำรายการนี้"),
            404: ("NOT_FOUND", "ไม่พบข้อมูลที่เข้าถึงได้"),
            405: ("METHOD_NOT_ALLOWED", "ไม่รองรับวิธีเรียกนี้"),
            409: ("CONFLICT", "ข้อมูลเปลี่ยนไป กรุณาตรวจใหม่"),
            429: ("RATE_LIMITED", "ส่งคำขอบ่อยเกินไป กรุณารอสักครู่"),
        }.get(response.status_code, ("HTTP_ERROR", "ไม่สามารถทำรายการได้"))
    response.data = envelope(code, message, details)
    return response


def csrf_failure(request, reason=""):
    return JsonResponse(envelope("CSRF_FAILED", "กรุณาโหลดหน้าใหม่แล้วลองอีกครั้ง"), status=403)


def server_error(request):
    return JsonResponse(envelope("INTERNAL_ERROR", "ระบบขัดข้อง กรุณาลองใหม่ภายหลัง"), status=500)
```

CSRF rejection ของ Django Middleware/Decorator ไม่ผ่าน DRF handler จึงมี `CSRF_FAILURE_VIEW` แยก ส่วน 500 นอก DRF View ใช้ `handler500` เมื่อ `DEBUG=False` สำหรับ Error จาก Proxy/URL ที่ไม่มีหรือหน้า HTML อื่น React ยังต้องมี Fallback ไม่คาดว่า Response ทุกตัวเป็น Envelope เสมอ

Import DRF handler ภายในฟังก์ชัน เพราะ Authentication class ใช้ CsrfFailed จากไฟล์นี้ หาก Import `rest_framework.views` ที่ระดับ Module อาจวนกลับระหว่าง DRF โหลดค่า Authentication จนเริ่มระบบไม่ได้

| Status | ใช้กับอะไรใน Contract |
| --- | --- |
| 400 | Validation หรือรูปแบบคำขอผิด |
| 401 | Authentication challenge ของ Scheme อื่นในอนาคต; Baseline Session ไม่บังคับใช้ |
| 403 | AUTHENTICATION_REQUIRED, INVALID_CREDENTIALS, CSRF_FAILED หรือ PERMISSION_DENIED ต้องอ่าน code |
| 404 | ไม่มี Task ในขอบเขตผู้ใช้ |
| 409 | Conflict ตามกติกาจริง เช่น Version ชน; CRUD ตัวอย่างยังไม่มี Version check |
| 500 | Error ภายใน ข้อความปลอดภัย ไม่เปิด Traceback/SQL |

ไม่ Map IntegrityError ทุกแบบเป็น 409 เพราะอาจเป็น Bug/ข้อมูลผิดคนละกรณี และการ Return Response ตรง ๆ จาก View จะไม่ผ่าน Handler นี้ ต้องใช้ Exceptions ที่ตกลงหรือสร้าง Envelope ให้ตรงเมื่อจำเป็น

## วิธีทดสอบ

ทดสอบ Error body กับ Status ทั้งคู่ รวม unhandled exception และ CSRF failure แบบ Anonymous ไม่ใช้แค่การดู Log ผู้ใช้ควรเห็นข้อความช่วยแก้ ส่วนทีมเก็บเหตุการณ์อย่างจำกัดตามสิทธิ์ ไม่ Log Password, Cookies, Headers ลับ หรือ Login body

## ข้อควรระวัง

Logger ตัวอย่างเก็บชนิด Exception กับ Method/Path เท่านั้น ยังไม่ใช่ระบบติดตาม Incident ครบ หากเพิ่ม Traceback/Context ต้องกรองข้อมูลลับและจำกัดผู้เข้าถึง ไม่ใช้ `DEBUG=True` เพื่อให้ผู้ใช้ส่งหน้าข้อผิดพลาดจริงกลับมา

## สรุปสิ่งที่ต้องจำ

- ตกลง Error envelope และ Status ร่วมกับ React
- Middleware errors อาจต้องมีเส้นทางตอบแยก
- 403 มีหลายสาเหตุ อย่า Logout ทุกครั้ง
- 500 ไม่ควรเปิดเผยรายละเอียดภายใน
