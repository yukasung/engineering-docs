# Environments & Secrets — แยกที่ทดสอบและค่าลับ

## เรื่องนี้คืออะไร?

Environment คือชุดแอป ค่าตั้ง และข้อมูลที่ใช้ทำงานร่วมกัน เช่น DEV หรือ UAT ส่วน Secret คือข้อมูลลับ เช่น SSH private key และรหัสผ่านฐานข้อมูล ต้องแยกตามปลายทางและให้เฉพาะงานที่จำเป็น

Git branch ไม่ใช่ Environment และ GitHub Environment เป็นกลไกจัดสิทธิ์หรือกติกาใน GitHub ไม่ได้สร้าง Server หรือฐานข้อมูลให้

## เตรียมอะไรก่อนเปิดใช้?

ตัวอย่างชื่อและหน้าที่ต่อไปนี้เป็น **ข้อเสนอสำหรับ Lab** ยังไม่ใช่นโยบายที่องค์กรอนุมัติ:

| ชื่อ | ใช้ทำอะไร | ก่อนย้ายรุ่นต่อ |
| --- | --- | --- |
| dev | ตรวจการเชื่อม Frontend/API/DB หลังรวมงาน | Smoke test และตรวจผล CI |
| uat | QA/ผู้รับผิดชอบงานตรวจความต้องการด้วยข้อมูลทดสอบ | บันทึกผลกรณีทดสอบและผู้ยืนยันจริง |
| production | ให้บริการผู้ใช้จริง | Project security/runbook, Approval และ Recovery พร้อม |

แต่ละที่ต้องมี Host/DB/Secrets ของตัวเอง อย่าชี้ UAT ไป DB ของ Production เพื่อทดสอบ ตัวอย่าง Deploy Workflow บทถัดไปเลือกได้เฉพาะ dev/uat ของ Docker Task Lab ที่จำกัดการเข้าถึง

### 1. ตั้ง GitHub Environment และกติกาก่อนรัน

1. สร้างชื่อ Environment ที่จะใช้ไว้ล่วงหน้า ไม่พึ่งชื่อจาก YAML ให้สร้างเองพร้อมค่าเริ่มต้น
2. จำกัด Deployment branches/tags ให้ตรง Trusted release branch และกำหนดผู้อนุมัติที่มีหน้าที่จริง
3. ถ้าใช้ Required reviewers ให้ตั้งการห้ามอนุมัติงานตัวเองและการ Bypass ตามนโยบายที่ตกลงไว้
4. ตรวจว่า GitHub plan และ Repository visibility รองรับ Protection ที่ต้องใช้จริง ชื่อ Environment อย่างเดียวไม่สร้าง Approval gate
5. ถ้ายังใช้ Gate ที่ต้องการไม่ได้ ให้หยุดการเปิด CD และใช้กระบวนการอนุมัติที่ตามรอยได้ก่อน ไม่ถือว่า Job ที่ไม่รออนุมัติปลอดภัยเท่ากัน

บทนี้ไม่ได้ตั้งค่า GitHub ให้ ดู [Environment protection rules](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments) สำหรับข้อจำกัดและความสามารถของบัญชีจริง

### 2. จัดค่าที่ต้องใช้

| ที่เก็บ | ชื่อตัวอย่าง | เหตุผล |
| --- | --- | --- |
| GitHub Environment variables | DEPLOY_HOST, DEPLOY_USER, DEPLOY_PORT | ปลายทางที่ผู้ดูแล Review แล้ว ไม่รับ Host จากผู้กด Run |
| GitHub Environment variables | FRONTEND_REPOSITORY, BACKEND_REPOSITORY | Allowlist เช่น ghcr.io/your-org/task-demo/frontend ต้องตรงชื่อ Lowercase จริง |
| GitHub Environment secrets | DEPLOY_SSH_KEY | Key ของ Deploy identity ที่เข้าถึงได้ตามขอบเขต |
| GitHub Environment secrets | DEPLOY_KNOWN_HOSTS | Host public key ที่ตรวจ Fingerprint ผ่านช่องทางเชื่อถือแล้ว |
| Server secret source | POSTGRES_PASSWORD, DJANGO_SECRET_KEY | ส่งเข้า Runtime บน Server ไม่ต้องส่งผ่าน CI สำหรับ Deploy นี้ |
| GitHub job token | GITHUB_TOKEN | Token ชั่วคราวสำหรับ Job; Image publish ใช้ packages:write เฉพาะงาน Trusted |

Known hosts ไม่ใช่ Private key แต่ต้องป้องกันการเปลี่ยนผิด เพราะใช้ยืนยันว่าเชื่อม Server ถูกเครื่อง ห้ามแก้ Host key mismatch ด้วย StrictHostKeyChecking=no หรือสแกนแล้วเชื่อ Key ใหม่ทันทีโดยไม่ตรวจ

Server ดึง Private image ด้วย Read-only Registry credential ที่ผู้ดูแลเตรียมไว้สำหรับ Docker identity ที่ใช้งาน ไม่ส่ง GITHUB_TOKEN ของ CI มาวางระยะยาวบน Host ดู [Secrets](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets)

### 3. แยก Build-time กับ Runtime

Build สร้างสิ่งที่จะปล่อย ส่วน Runtime คือค่าตอนเริ่มระบบ เช่น DB host/Secret ตัวอย่าง React ใช้ `/api` แบบ Relative URL คือเรียก API ผ่านเว็บที่เปิดอยู่ แล้วให้ Reverse proxy ส่งต่อไป Backend จึงใช้ Frontend image เดิมข้าม Environment ได้

ตัวแปร Frontend ที่ถูกฝังตอน Build เช่น VITE_* อ่านได้จาก Browser จึงไม่ใช่ที่เก็บ Secret หากต้องเปลี่ยน API URL ตามที่ทำงาน ให้เลือก Relative URL หรือออกแบบ Runtime config ของโครงการให้ชัด ไม่ Rebuild แล้วอ้างว่าเป็น Digest ที่ UAT ทดสอบแล้ว

## ตัวอย่างการใช้งานจริง

ทีมเลือก Release record จาก CI ที่ผ่านบน main ผู้ตรวจยืนยัน Commit และคู่ Digests ก่อน Deploy DEV จากนั้น QA ตรวจ UAT ด้วยคู่เดิม ส่วน Host/DB password ต่างกันตาม Environment หาก UAT ไม่ผ่านให้หยุด Promote และส่งแก้ผ่าน PR

เมื่อสร้างแอปที่มี Login จริง ต้องเพิ่มการตรวจ TLS, Session/CSRF, สิทธิ์ผู้ใช้ และกรณีที่ต้องถูกปฏิเสธด้วย Docker Task Lab ยังไม่ครอบคลุมเรื่องเหล่านี้

## ข้อควรระวัง

- ไม่ใส่ Secret ใน Git, Dockerfile, Build arguments, Image labels, Cache หรือ Release artifacts
- ไม่พิมพ์ env ทั้งหมด/ใช้ set -x กับคำสั่งที่มี Secret การ Mask logs ช่วยได้บางส่วนแต่ไม่ใช่การรับประกัน
- ค่าจาก PR/Fork ไม่ควรเข้าถึง Secrets หรือ Runner ที่เชื่อม Production ได้
- สิทธิ์ใช้ Docker/Deploy helper สูง ต้องให้ผู้ดูแลกำหนดสิทธิ์จำกัด ไม่มีคำสั่งเพิ่ม docker group หรือ sudo ALL ในคู่มือนี้
- OIDC ช่วยขอ Credential ชั่วคราวจากผู้ให้บริการที่รองรับได้ แต่ต้องตั้ง Trust policy จำกัด Repo/Branch/Environment ก่อน ไม่เปิด id-token:write โดยไม่มีงานใช้

## สรุป

- Environment, Branch และ GitHub Environment เป็นคนละเรื่อง
- ตั้ง Approval/Branch restriction ให้เสร็จก่อนเปิด CD
- Promote Digests เดิม แยก Runtime config/Secrets
- ให้สิทธิ์เฉพาะงานและตรวจปลายทาง SSH จริง
