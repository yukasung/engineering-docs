# Code Review

## เรื่องนี้คืออะไร?

Code Review คือการตรวจ Change ก่อน Merge เพื่อหาปัญหาและทำให้ทีมเข้าใจ Decision ร่วมกัน Reviewer ตรวจ Diff, Spec และผล Tests ไม่ได้ตรวจจากคำอธิบายของผู้เขียนเพียงอย่างเดียว

## ใช้เมื่อไร?

ใช้กับ Pull Request และ Change ที่ Project กำหนด Emergency fix ยังควรมี Review ที่ควบคุมได้และต้องนำการแก้กลับเข้าสู่ประวัติพัฒนาหลัก

## ทำอย่างไร?

1. อ่าน Objective, Requirements และ Out of scope
2. ตรวจ Diff ว่ามีไฟล์เกิน Scope หรือไม่
3. ตรวจ Correctness, Error handling และ Edge cases
4. ตรวจ Authentication, Authorization, Sensitive data และ Dependency change
5. ตรวจ Tests และ Validation ที่รันจริง
6. เขียน Finding พร้อมผลกระทบ ไฟล์ และเหตุผล
7. รัน Checks ใหม่หลังแก้ Finding สำคัญ

ใช้ [Inspect Changes](/development-workflow/git-pull-request/inspect-changes) อ่าน Diff และ [GitHub CLI](/development-workflow/git-pull-request/github-cli) ดู PR/Checks เมื่อ Repository ใช้ GitHub

## Finding แบบไหนควร Block merge?

Block เมื่อมี Bug ที่กระทบ Requirement, Unauthorized access, Data loss/corruption, Secret exposure, Unsafe migration, Regression สำคัญ หรือ Required tests ไม่ผ่าน ส่วน Style preference ที่ไม่มีผลต่อ Correctness อาจเป็น Recommendation ตามกติกาทีม

## Checklist

- [ ] Change ตรง Spec และ Acceptance criteria
- [ ] ไม่มี Unrelated changes
- [ ] Permission และข้อมูลสำคัญถูกตรวจที่ Backend
- [ ] Database/API compatibility ถูกพิจารณา
- [ ] Tests ที่เกี่ยวข้องผ่านและระบุสิ่งที่ไม่ได้รัน
- [ ] Documentation และ Migration อัปเดตเมื่อ Behavior เปลี่ยน

## ข้อควรระวัง

- AI review ช่วยหา Finding แต่ไม่แทน Human review
- Approval count และผู้ Merge ต้องมาจาก Repository policy จริง
- อย่า Merge เพราะ CI เขียวอย่างเดียว

## สรุป

- Review เทียบ Spec, Diff และผลตรวจจริง
- Finding ต้องอธิบาย Impact ไม่ใช่เพียง Preference
- Security/Data findings สำคัญควร Block merge
- หลังแก้ต้องตรวจซ้ำตามความเสี่ยง
